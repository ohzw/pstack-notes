コンテキストの守り方プレイブックを連ねても、Compaction に頼らずに進めるための規約

プレイブックから別のプレイブックへ作業をつなぐと、1 つのチャットに手順書の本文、調べた結果、差分、ログが積もります。やがてコンテキストが埋まり、Compaction（自動要約）に入ります。pstack には、コンテキストの量を見張る仕組みも、自動で退避する仕組みもありません。代わりに、プレイブックとスキルの書き方で 3 つのことを決めています。メインチャットには判断と要約だけを置く。状態はファイルに置く。溢れそうなら区切って、新しいチャットに引き継ぐ。

起きやすいこと1 つのチャットに積もる

プレイブックの手順は、同じチャットで別のプレイブックを開いたり、how や arena の結果を受け取ったりしながら進みます。手順書の本文、調べた結果、差分、CI のログが同じコンテキストに積もるので、作業が長いほど Compaction に入りやすくなります。

pstack の見方

原則 guard-the-context-window は、溢れたときの害を「推論の質が落ち、圧縮による欠落が生まれ、作業が止まる」と書いています（Context overflow degrades reasoning quality, creates compression artifacts, and halts progress.）。Compaction は頼る先ではなく、避ける対象です。principle-guard-the-context-window/SKILL.md

pstack の答え仕組みではなく書き方の規約

プラグインに入っているのは、スキル（Markdown）、エージェントの定義、補助スクリプトだけです。plugin.json にフックの定義はなく、コンテキストの量を測る処理もありません。plugin.json

規約の 3 つの柱
  1. メインチャットには判断と要約だけを置き、生データはサブエージェントが読む（2）
  2. 状態はファイルに置き、読み出しを短くする（3、4）
  3. 溢れそうなら Compaction の前に区切り、新しいチャットで再開する（5）

プレイブックからプレイブックを呼ぶための実行時の仕組みはありません。本文が別のファイルを指しているだけなので、同じチャットで呼ぶときのコストは、そのファイルを読む分です。呼び方は 3 通りあり、どれも同じチャットに手順を積み上げない形になっています。

2 WHERE情報の置き場所図は解釈

情報の置き場所は、メインチャット、作業ごとに起動するサブエージェント、コンテキストの外にあるディスクの 3 か所です。境界をまたいでよいものは、規則で決まっています。

パスで渡す

サブエージェントを起動するときの既定は file pointers not inlined context です。下調べの結果も、中身を貼らずにファイルの場所で渡します。poteto-mode/SKILL.md

生の出力は貼らない

swarm は結果をまとめるときに Do not paste raw worker dumps. と定めています。multi-phase-plan の探索役が返すのは、ファイルの場所、規約、テストコマンド、入口だけです（No inlined dumps.）。swarm/SKILL.md multi-phase-plan.md

生データは子が読む

長いトランスクリプト（Session pickup）、大きなプロファイル（Trace / Runtime forensics）、過去のチャット（recall）は、サブエージェントが読みます。メインに残すのは縮めた結論だけです。recall は The raw transcripts stay in the subagents. と書いています。session-pickup.md trace-forensics.md recall/SKILL.md

まとめ役も子に任せる

how と why は、調べる役だけでなく、結果を 1 つにまとめる役（explainer、synthesizer）もサブエージェントに任せます。親は返ってきた説明を提示するだけです。how/SKILL.md why/SKILL.md

毎回新しく起動する

修正のやり直し、追加作業、リトライ、キューの次の項目は、新しいサブエージェントに任せます。そのとき、元の brief、その後の指示すべて、前任の報告とブランチをまとめて渡します（consolidated scope）。既存のエージェントを再開するのは、チェックアウトや dev server のように、移しにくい状態がそこにあるときだけです。poteto-mode/SKILL.md

手順書は一致したものだけ開く

ルーターに載っているのは、1 行ずつの索引です。手順の全文は、一致したプレイブックのファイルを開いて読みます。原則の本文も、その原則を適用するときにだけ読みます。poteto-mode/SKILL.md

Interrupt-chained resumes silently drop directives, so fire a fresh subagent with consolidated scope rather than trusting a "done" summary. 割り込みで再開を重ねると、指示が黙って抜け落ちる。「完了」という要約を信じず、範囲をまとめ直した新しいサブエージェントを起動する。 poteto-mode/SKILL.md

長く動いたエージェントの要約を自動処理に任せず、残す要点を親が書き直して、新しいコンテキストで始め直す方式です。手動の Compaction と言えます。何を残すかを親が選べる点が、自動要約との違いです。解釈　Claude Code 向けの読み替えでも、resume は「新しいエージェントを起動し、前の結果を brief に貼る」になっています。claude-code.md

3 DISK状態はファイルに置く

コンテキストが消えても作業が消えないように、続きに要る状態はファイルに書きます。Orchestrate では、どのファイルにも書き手が 1 人だけいます（Every file has exactly one writer.）。orchestrate.md

ファイル中身使い方
preferences.md常設の命令（standing orders）。1 行に 1 つの制約spawn と resume のたびに渡す。再開を重ねると指示が薄れていくため（Directives decay across resumes）。同じ指示を 2 回書きそうになったら、行を足す orchestrate.md
units.tsv作業単位ごとの状態、ブランチ、PR、head SHA行をその場で書き換える orchestrate.md
ledger.tsv検証の判定。PR と head SHA の組ごとに 1 行「検証済みか」には、記憶でも transcript でもなく台帳が答える orchestrate.md
inbox/完了通知のポインタ報告の本文ではなく、報告ファイルのパスを積む（--report PATH） orch.ts
status.md今の状況表から作り直す。出来事を書き足していかない orchestrate.md
decisions.tsv判断ログ。1 行に 1 つの判断根拠は文章ではなくポインタで書く（Evidence is a pointer, not prose.） show-me-your-work/SKILL.md
計画書複数の PR にまたがる計画実行中は、ティックのたびに手順書を trunk から読み直す multi-phase-plan.md
再開メモ中断したときの状態と、再開したら最初にやること/tmp/<slug>-resume.md などに書く。判断ログがあれば、写さずにそれを指す pause-safely.md

読み出しを 1 行にするorch.ts

Orchestrate の状態は、orch という CLI を通して読み書きします。決まりは one command in and one line out です。追加したとき（99559f2、#187）の文面には、この後に to conserve context（コンテキストを節約するため）と理由が書かれていました。今の文面からは、この句が削られています。orchestrate.md

実装も短く返します。一覧は 4 行で切って残りを ... N more; use --json とし、orch status は counts、changed、gates open の 3 行だけを出します。orch.ts

要約された後も同じ runshow-me-your-work

判断ログは、1 つの run を one agent conversation, including its later turns and any summary of it と定めています。要約された後の会話も、同じ run です。後のターンで戻ってきた run は、まずログの末尾を読んで、他の run が書き足していないかを確かめます。show-me-your-work/SKILL.md

決まった処理はスクリプトにwatch-pr · sqlite

PR の状態は、watch-pr が READY、WAITING、BLOCKER などの判定を JSON で返します。トレースは sqlite に入れてから問い合わせます（Reach the queryable shape before you read.）。babysit.md trace-forensics.md

CI のログやトレースの生データを、エージェントが何度も読まずに済みます。解釈

4 SCALE規模ごとの体制図は解釈

どこまで分けるかは、規模で変わります。1 体で終わる作業はチャット内のプレイブックか Autonomous run に、PR の列は Autopilot に回します。Orchestrate を使うのは、エージェント 1 体の寿命を超える作業のときだけです（Route here when the work outlives any single agent.）。orchestrate.md

Orchestrate のコーディネーターは何日も動き続けるので、1 ターンを小さく保つための決まりが細かく書かれています。orchestrate.md

完了通知はキューに積む

Completions are queue events, not interrupts. 通知が来たら orch inbox push を実行して、元の作業に戻ります。その場で中身を読み込まず（Never deep-review inline.）、レビューが要るものは verifier の作業単位にします。

まとめて処理するのは 4 か所

溜まった通知を処理（drain）するのは、作業の区切り、track のまとめ、frontier の見張りに起こされたとき、人への報告の前の 4 か所だけです。drain のターンは orch status の 3 行で終え、詳細は status.md に任せます。

中間層は必要になってから

sub-coordinator は、1 回の drain で捌けない規模になってから置きます。層を挟むたびに、状況をつかむための前置きを払い直すからです（Each nested layer re-pays a full orientation preamble）。階層は 3 段まで、同時に動かす子は 1 回の drain で処理できる 10 体ほどです。

子の報告は 1 体 1 行に

sub-coordinator は、子の報告を生のまま上に渡しません（Never forwards raw child reports.）。子ごとに name、status、PR、head SHA、verdict と 1 行の説明にまとめます。

変化がなければ黙る

multi-phase-plan が定める定期チェック（ティック）では、表や変わらない障害を繰り返し書きません。何も見つからなければ、返信を書かずにターンを終えます（If the audit found none, end the turn with no reply text.）。Autopilot-full でも、何も変わらなかったティックは黙ります。multi-phase-plan.md autopilot-full.md

brief も単位に合わせる

2 行の修正に 4 KB の指示書を付けると、修正そのものより、書くのも従うのも高くつきます（A 4KB scaffold around a two-line edit costs more to write and obey than the edit.）。1 コマンドで済む単位なら、指示書を 1 段落に縮めます。

一晩に何十回も回るティックや drain のたびに、同じ状況報告や子の生の報告がメインチャットに積もるのを防ぐ決まりです。解釈

5 PAUSE区切りと再開図は解釈

それでも溢れそうなときは、Compaction を待たずに区切ります。ルーターは Pause safely を起動する条件として、明示の中断、オフライン、Cursor の再起動と並べて imminent context compaction を挙げています。poteto-mode/SKILL.md

Pause safelypause-safely.md

  1. 安全な区切りで止める。今の手順を終えるか取り消し、入れ子のサブエージェントも止める
  2. 止めるために不可逆な操作をしない。PR や push は、すでに出していた場合だけ
  3. 未コミットの編集を 1 つの wip: コミットにする
  4. 再開メモをコンテキストの外に書く。Compaction が理由のときは /tmp/<slug>-resume.md などのファイルに書き、判断ログがあればそれを指す

明示の指示でだけ動きます。「keep going」「going to bed, keep going」と言われたら止まりません。pause-safely.md

Session pickupsession-pickup.md

  1. 前の記録を探して読む。長いトランスクリプトはサブエージェントで読み、縮めた時系列だけをメインに残す
  2. ブランチ、着地済みの変更、残りの todo、決めたことから状態を組み立て直す
  3. 済みと未済を比べて再開点を決める。前の再現や完了済みの作業はやり直さない
  4. 残りの作業を該当プレイブックに渡す。pickup の手順はここで終わる
  5. 引き継いだ主張を、元のゴールに照らして実物で確かめる

前の記録は正しい入力として扱い、一から導き直そうとしません（The prior trail is authoritative input. Resist the bias to re-derive it.）。session-pickup.md

For the compaction trigger write it to a file like /tmp/<slug>-resume.md, because the in-context plan won't survive summarization. Compaction が理由のときは、/tmp/<slug>-resume.md のようなファイルに書く。会話の中にある計画は、要約を越えて残らないから。Pause safely を追加したときの文面で（2f3a47e、#115）、理由の部分はのちの簡潔化（e8d856f、#329）で削られた。

Orchestrate のコーディネーターも、作り直せる前提で書かれています。Cursor を再起動した後は、standing orders と units.tsv を読み直し、frontier を計算し直し、cloud の作業をエージェント ID ではなく PR とブランチで付け直します。ツールの失敗が続いたときは、終わったこと、置き場所、再開のコマンドをファイルに書いて終わります。orchestrate.md

6 LIMITS限界と使い方

限界

  • どれも文章で書かれた規約で、守らせる仕組みはありません。守るかどうかはモデル次第です。
  • Pause safely には This is explicit only. と書かれています。Compaction が近いことを pstack は検知しません。誰が「直前」と判断するのかも、本文には書かれていません。
  • サブエージェントの最終報告は、Task の戻り値として親のコンテキストに入ります。arena の候補比較（Read every candidate end to end before picking.）や Feature の diff レビューのように、リードが自分で読む段は親に積もります。中身を読まない役に徹するのは、Orchestrate のコーディネーターだけです。arena/SKILL.md
  • 原則ファイルの本文は Size phases and cap scope. で始まる 1 行だけです。初版にあった Isolate large payloads. などは、書かなくてもエージェントが従うとして b0b9c7a（#419）と 08bd59b（#571）で削られました。具体策は、ルーターと各手順の側に書かれています。

使う側の運用docs/guide

  • 話題を変えるときは new task と書きます。長いチャットには前の作業の文脈が溜まっているからです（A long chat accumulates context from the last task.）。調査の結論が出て修正に移るときも、修正を新しいタスクとして始めます。02-poteto-mode.md 03-understand.md
  • /poteto-mode は Custom Mode で起動します。毎ターン、指示がコンテキストに残ります。Enter で 1 回付けただけだと、チャットが進むにつれて薄れます（it fades as the chat moves on）。01-setup.md
