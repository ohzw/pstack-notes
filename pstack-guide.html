2 VERIFY検証スキルPt. 1

検証スキルは、エージェントが自分の作業を自分で確かめるための道具です。人間が確認役にならずに済むので、作業のループをエージェントだけで閉じられます。著者はこれを単なるスキルではなく重要インフラとして扱い、うまく作れば非エンジニアを含むチーム全体の出力が 100〜1000 倍になると書いています。

作る・保つ create / maintain

/create-verification-skill を実行すると、操作用の CLI と Feature Map を含む検証スキルができます。Grok Bot と Cursor で使っている検証スキルの共通部分を抜き出したメタスキルです。保守用の /maintain-verification-skill は日次ルーチンにして、少なくとも 1 日 1 回回します。pstack 同梱の Dr Eggbot にエンジニア役のボットを作らせ、作成と保守を任せることもできます。

技術スタックで差がつく

Electron や Web なら Chrome DevTools Protocol、iOS ならシミュレータが使えます。操作、デバッグ、パフォーマンスのトレースなど、手で開発するときと同じ道具をエージェントに渡すのが理想です。道具が乏しければ、lldb を使うツールや開発環境で動くサイドカーを作らせます。

著者は、検証のためにデバッグツールを自作すること、さらには技術スタックを変えることまで本気で勧めています。デバッグや制御が難しいスタックほど、エージェントは役に立たないからです。

Markdown ではなく CLI を渡す Build the Lever

アプリの操作とデバッグを小さな CLI にまとめます。使い捨てのスクリプトを書かせずに済むのでトークンが減り、手順も再現しやすくなります。開発用 DB のシード、認証とテストユーザー、ステージング環境への API 呼び出し、環境の立ち上げ手順も整えます。高度なことに進む前に、まずこの CLI を堅牢にします。

  • 組み合わせやすい API にする（Ousterhout の deep modules）
  • 破壊的な副作用があるコマンドには --dry-run を付ける
  • サブコマンドで機能を少しずつ見せる
  • エラーには、代わりに何をすべきかまで書く
  • --help を充実させる
  • 出力は JSON など機械が読める形式にする

Feature Map

アプリの全機能について、何をするものか、ユーザーとしてどうたどり着くかをまとめた地図です。references/features に置き、その中の README.md が目次になります。中身はエージェントがアプリを一通り回って書きます。

著者はこれを「実体化されたメモリ」と呼びます。チームの意思決定が形になったコードベースを、トークンを節約できるように圧縮したものです。スキルの中にあるので、コードベースに関わる全員が同じ地図を使えます。CLI と Feature Map の組み合わせが、pstack の検証スキルが強い主な理由だとしています。

4 UNDERSTAND理解するPt. 2

エージェントを使えば、コードをよく知らなくても変更できます。それでも品質とユーザー体験を保つのは難しいままです。著者がよく見る失敗は、指示が足りず意図が伝わらないことと、正しく作業するための文脈が足りないことの 2 つです。どちらも、コンテキストウィンドウに質の高い文脈を入れられるかどうかで決まります。Pt. 2 の告知では、これを「自分より賢い相手を監督する技術」と呼んでいます。

自分の言葉で言い直させる indirect prompt

望みを直接伝えず、エージェントに言わせます。たとえば Slack の報告スレッドを読ませ、根本の問題を平易な言葉で言い直させます。効果は 3 つあります。

  • 雑多な会話を、整った問題文にまとめさせられる
  • 的外れな手がかりにこだわっていても、コードを書く前に直せる
  • 間違っているかもしれない自分の仮説で、エージェントを誘導せずに済む

最新モデルは人間よりうまくコードを書くので、細かく指示しすぎず、達成したいことだけ伝えて解き方は任せます。

メンタルモデルを作るスキル

/teach人間にわかる言葉で説明させる。「なぜ別の方法ではなくこうしたのか、トレードオフは何か」を問うときに使う。内部で /how と /why を呼ぶ
/how実行時の仕組みを追う。範囲が複数のディレクトリやサービスにまたがれば、速いモデルで探索役を並列に起動する
/whyなぜそう書いたかを調べる。Git 履歴、PR のコメント、Linear、Notion、Slack、Datadog、Sentry、分析基盤のイベントなどを並列に照会する
/recall過去のチャット履歴から最近の文脈を呼び戻す。何日もかかる作業を新しいチャットで続けるときに使う

説明させると、エージェントも裏付けを取ることになります。最新モデルでも、コードを読まずに断言することがよくあるからです。

5 DESIGN設計するPt. 2

多くのハーネスの plan mode は、実装の詳細を書きすぎる一方で、それ以外の記述が足りない、と著者は見ています。「計画を信じない」というのは半分冗談で、実際にはコードで計画します。よくある失敗は、エージェントが最初に出した設計をそのまま採ることと、実証のないまま計画をいじり続けることです。

README から逆算する README driven

共有コードやパッケージは、架空の利用者に API を説明する README から書き始め、実装へ逆算します。社内のデスクトップ向けフレームワーク Dune ではチュートリアルから書き始めましたが、エージェントの文章が使えず、先に /technical-writing を作りました。最初の README は、次の 4 種類が 1 本に混ざっていたそうです。

チュートリアル初心者が手を動かして学ぶ
ハウツー経験者が特定の問題を解く手順
リファレンス仕組み、API、設定の正確で網羅的な記述
解説背景、設計判断、トレードオフ

/technical-writing は Diátaxis に沿ってこの 4 つを分け、/unslop を通して読みやすくします。書いた README は、エージェントが自分の作業を照らし合わせる目標にもなります。

technical-writing/SKILL.mdunslop/SKILL.md

試作で比べる prototype playbook

1 つの目標に何度も挑ませ、最良の案を選ばせます。見た目だけでなく、機能やバグ修正の解き方の比較にも使えます。UI の操作なら 2〜3 案を切り替えスイッチの裏に並べ、/control-app で操作して撮影し、タイミングやレイアウトを実測します。疑問には人間の返事を待たず、実証で答えさせます。

3 段の頼み方

新しい仮想化エンジンを設計させた例です。問題を小さな断片ではなく、人間と同じ視野で見られるだけの文脈を先に渡します。

  1. 過去 7 日分の作業を /recall で呼び戻し、/how と /why で今の実装を理解させる
  2. ちらつきと揺れを根本からなくす設計を、利用者向けのチュートリアルを書くところから始めさせる
  3. 新しい方式が今のものより優れていることを、/teach で証明させる

最後の証明の段で、検証スキルのような道具が効きます。

大きな変更は /architect で

エンジニアはアーキテクチャ、データ構造、システム同士の連携に時間を使い、実装の詳細はエージェントに任せる、というのが著者の考えです。/architect は設計を 5 段に分けます。

  1. 問題の把握: 影響を受ける部分に /how と /why をかけ、担当範囲と制約をつかむ
  2. スケッチ: 独立した候補作成役を、なるべく別のモデルファミリーで並列に動かす。各候補は呼び出し側のコード例、主要な型、公開関数のシグネチャ、短い根拠を出す
  3. 相互審査と統合: メインとは別のモデルの審査役が、厳格な基準で候補を比べる
  4. スケッチに沿った実装: 仮の中身を本物にする。想定外の引数や状態が要れば、そのずれを報告する
  5. 誤っていたら捨てる: 設計の誤りが実証されたら、全部捨ててやり直す

別系統のモデルの組み方は「モデル割り当て」の章にあります。

architect/SKILL.md

設計が誤っている兆候

関係のない呼び出し箇所に同じ回避策が出てくる。any や強制キャストのような抜け道が要る。著者はこれらを、設計が誤っている実証的な証拠とみなします。

逆に、抽象的な計画を批判的にレビューすることはしません。エージェントが理論上のリスクや、実際には起きないエッジケースを作り出し始めるからです。抽象的な段階で計画をいじり続けず、試作と検証で答えを出させます。

6 PLAN計画と実践Pt. 2

計画用のスキルはありませんが、多段階の計画用プレイブックがあります。満足できる設計ができた後に、実行計画へ落とし込むために使います。各タスクは証拠と検証を中心に組まれ、テストが通っただけでは検証済みとみなしません。実際にコードを動かして確かめる必要があります。計画の構造と書式はスクリプトで検査され、承認後は 1 項目ずつ、小さく自己完結した PR として進みます。1 週間かかるような案件では、他のエージェントに知らせるために計画を一時的にコミットすることもありますが、終わったら消します。poteto-mode/playbooks/multi-phase-plan.md

場面頼むことエージェントの進め方
原因不明の障害バックグラウンドワーカーが定期的にタイムアウトする理由を調べ、わかっていること、使ったデータ、有力な仮説を出させるコード、メトリクス、過去のコミットを並列に調べる
新しいサービス境界外部 webhook のレート制限を、まず /architect にかける。未解決の疑問は試作で答えさせ、進める前にレビューする既存の構成を把握し、複数のモデルで競合する設計を出し、使い捨ての試作で比べる
複数 PR の移行UI ライブラリ全体を StyleX に移す。小さく検証できる PR に分け、各 PR に見た目の回帰テストと実機での検証手順を付ける。結果はバグも含めて元と同一にする独立した段に分け、監査できるチェックリストを書く
Slack の報告スレッドに文脈が十分なら /poteto-mode にそのまま任せる。または /control-app で再現させ、main で再現したら直して動画を出させる多くのスキルは /poteto-mode が自動で使うので、大半はこれだけで足りる

著者の結論は、Plan Mode の長い計画は進んでいるという錯覚を与えるだけで、中身が薄いことが多い、というものです。調査、実証、厳密な検証を組み合わせれば、エージェントとの開発は賭けではなく、予測と再現ができるものになるとしています。
