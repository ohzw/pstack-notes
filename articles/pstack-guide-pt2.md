- 告知の投稿では「自分より賢い相手を監督する技術」を学ぶ回だと紹介されています。
- この文書は原文を日本語で要約したもので、全文訳ではありません。原文の図と画像は含めていません。

## 導入

- 前回の要点は、エージェントが自分の作業を検証できなければ、人間がボトルネックのままになり、一日中エージェントの面倒を見ることになる、というものでした。
- 今回は、検証が回るようになった後の問い、つまり「何を作るかをどう決めるか」を扱います。対象は調査、計画、プロトタイピング、アーキテクチャです。

## 自分より賢い相手を監督する技術

- 2024 年ごろまでは、変更する前にシステムのメンタルモデルを頭の中に作る必要がありました。エージェントはこの壁をなくしましたが、コードの品質とユーザー体験を保つことは今も難しいままです。
- 著者がよく見る失敗は 2 つあります。
  1. 指示が足りない、または曖昧で、エージェントが意図をつかめない
  2. 正しく作業するための文脈が足りない
- どちらも、コンテキストウィンドウに質の高い文脈を入れられるかどうかの問題です。

### 自分の言葉で言い直させる

- 最新モデルは人間よりうまくコードを書きます。細かく指示しすぎず、達成したいことは伝え、解き方は任せる、という加減が要ります。
- 手法の 1 つが**間接的なプロンプト**です。望みを直接伝えるのではなく、エージェント自身の言葉で引き出します。たとえば Slack の報告スレッドを読ませ、根本の問題を平易な言葉で言い直させます。
- これには 3 つの効果があります。
  - 雑多な会話を、構造の整った問題文にまとめさせられる
  - エージェントが的外れな手がかりにこだわっていても、コードを書く前に直せる
  - 自分の仮説（間違っているかもしれない）でエージェントを誘導せずに済む

### メンタルモデルを作る

- `/teach` は、エージェントに直感的な説明をさせるスキルです。内部で `/how` と `/why` を呼びます。
  - `/how`: 実行時の仕組みを追います。対象が複数のディレクトリやサービスにまたがる場合は、Grok などの速いモデルで探索エージェントを並列に起動します。
  - `/why`: 動機と意図を調べます。Git 履歴、PR のレビューコメント、Linear、Notion の設計文書、Slack、Datadog、Sentry、コードの変遷、分析基盤のイベントを並列に照会します。
- 「なぜ別の方法ではなくこう実装したのか、どんなトレードオフがあったのか」を `/teach` で尋ねます。
- この調査は人間だけでなくエージェント自身の役にも立ちます。最新モデルでも、データやコードを確かめずに断言することがよくあります。説明させる過程で裏付けを取らせることになります。

### 過去の会話から学ぶ

- 何日もかかる作業では、新しいチャットを始めるたびに文脈を作り直すことになります。
- 過去のトランスクリプトは文脈の宝庫です。`/recall` はチャット履歴から最近の文脈を引き出します。
- `/teach`、`/recall`、`/how`、`/why` を使って、著者は自分のメンタルモデルも最新に保っています。

## 逆算する

- 著者の見立てでは、多くのハーネスの plan mode は実装の詳細を書きすぎる一方、それ以外の記述が足りません。著者は「計画を信じない」と冗談めかして言いますが、実際にはコードで計画しています。
- 共有コードやパッケージには **README 駆動開発**を使います。README を先に書き、架空の利用者向けに API を説明するところから、実装とアーキテクチャへ逆算していきます。
- 例として、社内のデスクトップ向けクライアントフレームワーク Dune の開発を挙げています。チュートリアルから書き始めましたが、エージェントの書く文章が使い物にならなかったため、先に `/technical-writing` スキルを作りました。最初の README は、チュートリアル、ハウツー、設計の説明、API リファレンスが 1 つの文書に混ざっていたそうです。
- `/technical-writing` は Diátaxis の枠組みに沿って、文書を 4 種類に分けます。あわせて `/unslop` を通し、読みやすい文章にします。
  1. チュートリアル: 初心者が手を動かしながら学ぶ
  2. ハウツーガイド: 経験者が特定の問題を解く手順
  3. リファレンス: 仕組み、API、設定の正確で網羅的な記述
  4. 解説: 背景、設計判断、トレードオフの説明
- この形で書いた計画は、エージェントが自分の作業を照らし合わせる具体的な目標になり、人間にとっても何が作られるのかがわかりやすくなります。
- 3 段構成のプロンプト例があります。
  1. 過去 7 日分の仮想化の作業を `/recall` で呼び戻し、`/how` と `/why` で現在の実装を理解させる
  2. ちらつきと揺れを根本からなくす新しい仮想化エンジンを設計させる。最初に「React アプリをどう仮想化するか」のチュートリアルを書かせる
  3. 新しい方式が今のものより優れていることを `/teach` で証明させる
- 狙いは、エージェントが問題を小さな断片ではなく、人間と同じ視野で見られるだけの文脈を引き出すことです。最後の証明の段では、検証スキルのような道具が効きます。

## 百回測って一回で切る

- 計画でよくある失敗は 2 つです。
  1. エージェントが最初に出した設計をそのまま採る
  2. 実証がないまま計画をいじり続ける
- pstack では、並列エージェントを使って「二度測って一度で切る」を限界まで推し進めます。その手段が**プロトタイピングのプレイブック**です。
- プレイブックはスキルではなく、`/poteto-mode` の中にある参照ファイルです。トークンを節約するため、タスクの種類に応じて必要なものだけが読み込まれます。v0.15.0 時点で 23 本あり、エージェントが自動で使います。
- プロトタイピングでは、1 つの目標に何度も挑戦させ、最良の案を選ばせます。見た目の試作だけでなく、機能やバグ修正の解き方の比較にも使えます。
- UI の操作を試すときは、2〜3 案を簡単な切り替えスイッチの裏に並べます。`/control-app`（Pt. 1 で作った検証スキル）で操作してスクリーンショットを撮り、実際のタイミングやレイアウトを測ります。
- プロトタイピングは「コードで行う計画」です。エージェントに問題の範囲を探らせ、予想外の案を出す余地を与えます。疑問には人間の返事を待たず、実証で答えさせます。

### 大きな変更のアーキテクチャ（`/architect`）

エージェント時代のエンジニアは、アーキテクチャ、データ構造の選択、システム同士の連携に時間を使い、実装の詳細はエージェントに任せる、というのが著者の考えです。`/architect` は設計を次の 5 段に分けます。

1. **問題の把握**: 影響を受ける部分に `/how` と `/why` をかけ、現状の担当範囲と制約をつかむ
2. **スケッチ**: 互いに独立した候補作成役を並列に起動し、なるべく異なるモデルファミリーを使う。各候補は、呼び出し側のコード例、主要な型定義、公開関数のシグネチャ、短い根拠を出す。インターフェースの深さ、性能の低いモデルが使ったときの失敗のしかた、設計上の危険信号の一覧も確認する
3. **相互審査と統合**: メインとは別のモデルを使う審査役が、厳格な基準で候補を評価する
4. **スケッチに沿った実装**: 仮の中身を本物のロジックに置き換える。想定外の引数や状態が必要になったら、そのずれを報告する
5. **誤っていたら捨てる**: 設計の誤りが実証されたら、すべて捨ててやり直す

- 関係のない呼び出し箇所に同じ回避策が出てくる、`any` や強制キャストのような抜け道が必要になる。こうした兆候は、設計が誤っている実証的な証拠とみなします。
- 著者は抽象的な計画を批判的に検討するレビューを行いません。エージェントが理論上のリスクや、実際には起きない複雑なエッジケースを作り出し始めるからです。

## それでも計画書が欲しい場合

- 計画用のスキルはありませんが、多段階の計画用プレイブックがあります。設計が固まった後、実行計画に落とし込むために使います。
- 計画の各タスクは、証拠と検証を中心に組み立てられます。テストだけでは検証として不十分で、実際にコードを動かして確かめて初めて検証済みとみなします。
- 計画の構造と書式はスクリプトで自動チェックされます。承認後は 1 項目ずつ、小さく自己完結した PR として実行されます。
- 1 週間かかるような大きな案件では、計画を一時的にコミットして他のエージェントに進行中の作業を知らせることもあります。ただし終わったら削除し、残しておきません。

## 実践例

1. **原因不明の本番障害の調査**: バックグラウンドワーカーが定期的にタイムアウトする理由を調べさせます。エージェントはコード、メトリクス、過去のコミットを並列に調べ、わかっていること、使ったデータ、有力な仮説を報告します。
2. **新しいサービス境界の設計**: 外部 webhook のレート制限です。まず `/architect` にかけ、未解決の疑問はプロトタイプで答えさせ、先に進む前に人間がレビューします。
3. **複数 PR に分けた移行**: UI ライブラリ全体を StyleX に移行します。小さく検証できる PR に分け、各 PR に見た目の回帰テストと実機での検証手順を付けます。仕上がりは元と完全に同一、バグも含めて同じにすることを求めます。
4. **Slack の報告への対応**: スレッドに文脈が十分あれば `/poteto-mode` に「やって」とだけ指示します。あるいは `/control-app` で再現させ、main ブランチで再現したら修正して、証拠の動画を出させます。ほとんどのスキルは `/poteto-mode` が自動で使うので、大半の場面ではこれだけで足ります。

## 計画の技術

- Plan Mode は、エージェントが正しくやってくれると自分を納得させるために使われがちです。しかし抽象的な計画は、進んでいるという錯覚を与えるだけです。長い計画は生産的に見えても、中身が薄いことが多いと著者は言います。
- 調査、実証、厳密な検証を組み合わせて計画すれば、エージェントとの開発は賭けではなくなり、予測と再現ができるものになる、というのが結論です。
