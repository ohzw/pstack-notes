pstack の骨格スキルの束を、ワークフローとして動かす仕組み

pstack の中身は、スキル（Markdown）とエージェントの定義と補助スクリプトだけで、実行エンジンもフックもありません。それでも依頼を受けると、決まった手順を順に進め、手順ごとに確かめ、決まった形で報告します。このページは、23 本のプレイブックや個々のスキルといった中身を省き、それらをつなぐ骨格だけを描きます。1 本のルーターが手順書を選び、その手順を todo に写し、手順がスキルを名前で呼ぶ。自分用のワークフローを組むときの見取り図になるように、骨格を支える決まりと、足場に求める機能も並べます。

2 RUN1 回の流れ図は解釈

依頼を 1 件受けると、メインチャットは次のように進みます。手順を todo に写すのは最初の 1 回だけで、あとは todo を 1 つずつ取り、確かめてから次へ進みます。

todo が進み具合を持つ

省く手順も skip: 理由 を付けて残します（A step you choose not to do stays in the list with a one-line skip: <reason>.）。写した一覧そのものが、どこまで進んだかの記録になります。解釈 poteto-mode/SKILL.md

通るまで次へ進まない

作業を確かめられる単位に分け、今の単位が通るまで次へ進みません（don't advance until the current one is green）。figure-it-out は判定を VERIFIED、NOT VERIFIED、INCONCLUSIVE に分け、INCONCLUSIVE を合格に数えません。principle-sequence-verifiable-units/SKILL.md figure-it-out/SKILL.md

やり直しは新しい子に

直し、追加の作業、再試行は、新しいサブエージェントに任せます。元の指示、その後の指示すべて、前任の報告とブランチをまとめて渡します（consolidated scope）。割り込みで再開を重ねると、指示が黙って抜け落ちるからです。poteto-mode/SKILL.md

終わり方は先に決まっている

各プレイブックの最後にある太字の Reply が、報告に入れるものを決めます。書き方はルーターの Writing the reply にまとめてあります。コードを変えるプレイブックは、最後に Opening a PR を実行します。poteto-mode/SKILL.md opening-a-pr.md

3 ENGINEエンジンとの対応解釈

pstack を、手順を実行するワークフローエンジンに見立てると、部品は次のように対応します。違うのは、どの部品も機械が実行するのではなく、モデルが読んで従う文章だという点です。

エンジンの部品pstack での実体書き方の要点
定義ファイルプレイブック。番号付きの Markdown手順にはスキルの名前と関門を書き、やり方は書かない
振り分けルーターのプレイブック索引依頼と照合するのはモデル。合うものが無ければ figure-it-out がその回の手順を作る
実行状態todo リスト手順を一字一句写す。省いた手順も理由付きで残す
タスクスキル「the name skill」と書けば呼べる。中身は書き写さない
ワーカーサブエージェント作業ごとに新しく起動する。モデルは役割で決まる
イベントフック常時トリガー「条件 → スキル」の 1 行。発火を判断するのもモデル
遷移の条件関門と、次へ渡す先「判定できない」は不合格だと書いておく
共有の規約原則判断を変えた原則を、返信で名指しさせる
環境設定pstack-models.mdc行が無ければ既定値。スキルの本文は書き換えない
チェックポイント判断ログ・wip コミット・再開メモPause safely が書き、Session pickup が読む
戻り値の型Reply 欄と Writing the replyプレイブックには、その作業に固有の項目だけを書く

エンジンが無い分、pstack は次の 6 つで手順を守らせようとしています。

入口以外は自分から動かない

56 本のスキルのうち 55 本に disable-model-invocation: true が付いています。説明文が依頼に似ていても、モデルが自分から読み込むことはありません。cursor.com/docs/skills

委譲先にも同じ規則を読ませる

poteto-agent は作業の前にルーターを全文読みます。汎用のサブエージェントで代えると、この読み込みが抜けてやり方がずれる、と README は書いています（substituting generalPurpose skips that read and drifts）。README.md

読んだかを名指しさせる

返信では、判断を変えた原則と、変わった選択を名指しします。名指しできるのは、その会話で葉の SKILL.md を読んだ原則だけです（Cite only principles whose leaf SKILL.md you read this session.）。poteto-mode/SKILL.md

決まった処理はスクリプトに

check-plan.mjs は、計画書に要る節と項目がそろっているかを検査します。watch-pr は PR の状態を判定し、READY や WAITING などを JSON で返します。check-plan.mjs babysit.md

守られたかを試す

eval プレイブックは、候補が実際に開いたファイルを会話記録で確かめ、本人の申告では採点しません。候補には、評価中だと分かる言葉を見せません。eval.md

繰り返す指示は構造に

同じ指示を 2 回書きそうになったら、文章を足さずに、lint、メタデータ、実行時の検査、スクリプトにします。リポジトリ全体には /correct を使います。principle-encode-lessons-in-structure/SKILL.md 09-make-it-yours.md

それでも、どれも文章で書かれた規約で、守るかどうかはモデル次第です。この限界は コンテキストの守り方 の 6 章でも扱っています。

5 BUILD自分用に組む解釈

pstack が用意している道と、骨格だけを真似る道があります。

pstack の上に自分のモードを足す/automate-me

最近の会話記録から自分のやり方を拾い、<名前>-mode のスキルを下書きします。pstack は土台に残り、自分のルーターが poteto-mode の隣に並びます（you keep pstack as the base and end up with your own routing skill alongside poteto-mode）。README.md

下書きは disable-model-invocation: true が既定です。poteto-mode は形の見本として読み、中身は写しません。他のスキルは書き写さず、パスで指します。automate-me/SKILL.md

骨格だけ真似て組む解釈

図 1 の箱を、そのまま自分のファイルに置き換えます。最初から全部はいりません。ガイドは、小さく始め、同じ失敗が 2 回出たらスキルか検査を足すよう勧めています（add a skill or a check when the same failure shows up twice）。09-make-it-yours.md

skills/
  <you>-mode/                  入口のルーター
    SKILL.md                   常時トリガー・原則の索引・共通の規則・プレイブックの索引
    playbooks/<task>.md        責任・手順・関門・次へ渡す先・Reply
    references/                ルーターとプレイブックだけが読む資料
    scripts/                   決まった処理（検査・判定）
  <tool>/SKILL.md              手順から名前で呼ぶスキル。並列起動もここ
  principle-<rule>/SKILL.md    判断の基準を 1 つ
agents/
  <you>-agent.md               委譲先。最初にルーターを全文読む
rules/
  models.md                    役割 → モデル。常に読み込まれる

足す順番

  1. ルーターを作る。最初は共通の規則（自律の範囲と返信の形）だけでよい。明示でだけ起動する印を付ける
  2. いちばん多い作業のプレイブックを 1 本書く。手順はスキルの名前で書き、関門と Reply を入れる
  3. 同じ手順が 2 本目のプレイブックにも出てきたら、スキルに切り出してパスで指す
  4. 同じ指摘を 2 回したら、原則か、検査のスクリプトにする
  5. 作業を並列に回し始めたら、委譲先の定義と、役割 → モデルの設定を足す
  6. 長い作業や離席が増えたら、判断ログと、止めて再開する手順を足す

避けること

  • プレイブックに知識を書き込む。判断の理由は原則に、やり方はスキルに置き、プレイブックには呼ぶ順番と関門だけを書く（pstack のプレイブック の 5 章）。
  • 他のスキルの中身を書き写す（Delegate to other skills by path. Don't restate.）。authoring-a-skill.md
  • 委譲先にプレイブックそのものを回す。依頼を受けたチャットが手順を持つ（Never spawn a poteto-agent to run the playbook itself.）。poteto-mode/SKILL.md
  • 作業の途中で、調子の悪いスキルを直す。別の PR で直し、作業は止めない。09-make-it-yours.md
  • スキルの変更を試さずに入れる。eval プレイブックで、同じ依頼を伏せた条件で比べる。eval.md

詳しくは、プレイブックの形とスキルとの境目を pstack のプレイブック、並列起動を プレイブックと fan out、役割とモデルを pstack のモデル割り当て、状態の置き場を コンテキストの守り方 で扱っています。

一言で。pstack の骨格は、明示でしか起動しない 1 本のルーターが手順書を選び、その手順を todo に写し、手順がスキルを名前で呼ぶ、というつなぎ方です。実行エンジンが無い代わりに、todo リストが進み具合を持ち、ファイルの名前が呼び出し先を決め、関門と Reply が終わり方を決めます。解釈
