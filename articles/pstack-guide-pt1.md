## 導入

- pstack は、著者が厳密なエンジニアリング作業に使う個人用のスキル集です。これを使って、月 2,000 件の PR を確信を持って本番に出していると著者は書いています。
- 著者は以前、PR 数や行数を見栄の指標と見ていました。エージェントを使って品質を保ったまま量を出せるなら量にも意味がある、と考えを改めています。
- 例として Grok Bot を挙げています。著者は約 2 か月前から関わり、今はチームが 1 日に数百件の PR を入れています。その中で、コードの監視、リファクタ、lint や検査の追加、機能開発を並行して進め、品質を保っています。
- プロトタイプ直後で勢いがあり人が次々に加わっていた時期に、停止なしでコードベース全体を土台から作り直しました。エンジニア以外の貢献者が増えても崩れない土台にするためです。これができたのは pstack があったからだと著者は述べています。

## 検証こそすべて

- 最も重要なのは質の高い**検証スキル**です。単なるスキルではなく重要インフラとして扱うべきもので、うまく作れば非エンジニアも含めたチーム全体の出力が 100〜1000 倍になると著者は言います。
- 検証とは、エージェントが自分の作業を自分で確かめられることです。人間がボトルネックにならず、エージェントだけで作業のループを閉じられます。

### 検証スキルを作る

- pstack を入れて `/create-verification-skill` を実行します。pstack 同梱のボット作成ボット「Dr Eggbot」にエンジニア役のボットを作らせ、そのボットに作成を任せることもできます。保守用の `/maintain-verification-skill` は日次ルーチンにします。
- このスキルは、Grok Bot と Cursor で使っている検証スキルの共通部分を抜き出したメタスキルです。
- 技術スタックの選び方で効果が変わります。Electron や Web なら Chrome DevTools Protocol（CDP）、iOS ならシミュレータが使えます。手で開発するときと同じように、操作、デバッグ、パフォーマンスのトレースができる環境をエージェントに渡すのが理想です。使えるランタイムが乏しければ、lldb を使ったツールや開発環境で動くサイドカーなどをエージェントに作らせます。
- 著者は、デバッグツールを自作すること、さらには技術スタックを変えることまで本気で勧めています。デバッグや制御が難しいスタックほど、エージェントは役に立たなくなるからです。

### 再現できる形にする

- pstack の原則「Build the Lever」に従い、Markdown の説明だけでなく道具を渡します。検証スキルの場合は、アプリの操作とデバッグをスクリプト化した小さな CLI を作ります。使い捨てのスクリプトを書かずに済むのでトークンが減り、再現やテストもしやすくなります。
- 開発環境も整えます。開発用 DB へのシードデータ投入、認証とテストユーザー、テスト／ステージング環境への API 呼び出し、環境構築を毎回同じ手順で行えることが対象です。
- 高度なことに手を出す前に、この CLI を堅牢にしておきます。エージェントが使いやすい CLI の条件は次のとおりです。
  - 組み合わせやすい API にする（John Ousterhout の deep modules の考え方）
  - 破壊的な副作用があるコマンドには `--dry-run` を付ける
  - サブコマンドで機能を少しずつ見せる
  - エラーメッセージを詳しくし、代わりに何をすべきかまで示す
  - `--help` を充実させる
  - 出力は JSON など機械が読める形式にする

### 並列化には worktree ではなく Cloud Agents を使う

- 並列化しようとすると worktree を考えがちですが、著者は勧めていません。ストレージとマシン資源を大きく消費し、並列数は 10 程度が限界だからです。
- Cursor の Cloud Agents は Cursor 側の実マシンで動きます。依存パッケージのインストール、アプリの起動、動画やスクリーンショットの撮影、ユーザーと同じ操作ができます。初回のセットアップはエージェントが手伝い、初回ビルド後にスナップショットが保存されるので、2 回目以降は速く起動します。
- クラウドで数百のサブエージェントを並列に動かす方法は、後の回で扱う予定です。

### Feature Map

- アプリが複雑になると、エージェントは目的の機能を見つけにくくなります。Feature Map は、全機能について、何をするものか、ユーザーとしてどうたどり着くかをまとめた検索しやすい地図です。
- `/create-verification-skill` を実行すると `references/features` ディレクトリと README.md ができます。README が地図の本体で、主要機能の概要と詳細ページへのリンクが並びます。中身はエージェントがアプリを一通り回って作るので、手で書く必要はありません。
- pstack の検証スキルが強い主な理由は、CLI と Feature Map の組み合わせにあります。
- 著者は Feature Map を「実体化されたメモリ」と呼んでいます。コードベースはチームの意思決定が形になったもので、究極のメモリです。Feature Map はそれをトークン節約のために圧縮したものです。スキル内の Markdown なので、コードベースに関わる全員で共有されます。
- そのため保守が重要で、`/maintain-verification-skill` を最低 1 日 1 回実行します。作業中にエージェントが自分で更新することもあり、漏れたものをこのスキルが拾います。

## 検証スキルの使い方

- 作例は https://github.com/poteto/verification-skill-example にあります。
- プロンプトは `/poteto-mode` で始めます。Cursor では補完時に Opt+Enter を押すと Custom Mode として固定され、毎ターン、スキルを使うよう促されます。
- **新機能**: `/poteto-mode` で実装させ、`/control-app`（`/create-verification-skill` で作ったスキル）で検証させ、証拠として動画とスクリーンショットを出させます。Grok Bot では、ボットに直接作業させず Cloud Agent を起動するよう頼みます。ボットの手を空け、コンテキストを汚さないためです。ボットはクラウドエージェントを監督する調整役という位置づけです。
- **パフォーマンス**: 現状のトレースを取り、改善点を見つけて修正し、`/control-app` と `/swarm` で効果を確かめます。`/swarm` は任意の数のクラウドエージェントに検証スキルを走らせるスキルです。十分なサンプル数で改善を確認したり、ファジングで退行を探したりできます。
- **ユーザー報告の自動再現**: Grok Bot の routines や Cursor Automations に組み込みます。Slack に届いたフィードバックをボットが監視し、クラウドエージェントで再現を試みます。検証スキルと Feature Map の出来がよければ、自動修正まで任せられます。

## 検証スキルに投資する

- CLI の改善を続け、重要インフラと同じように扱います。オンコール当番を置いてもよいほどだと著者は言います。
- 検証スキルは、このシリーズで紹介する他のスキルの土台になります。
